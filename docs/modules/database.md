# Database

This note covers the Postgres schema (Prisma 7 on Supabase): how it changes, how it is seeded, and the three clients that talk to Supabase. Every module reads and writes through server actions that use the Prisma client here. Developers work with this module; end users never see it directly.

**Related:** [[architecture]] · [[conventions]] · [[auth]] · [[campus-scoping]] · [[settings-lookups]] · [[assessments]] · [[checklist-editor]]

## Essentials

Read this before changing `prisma/schema.prisma`, writing a `prisma/manual/*.sql` file, seeding, or touching the Prisma or Supabase clients.

> **IMPORTANT / DISALLOWED COMMANDS:**
> Do NOT execute destructive or direct database modification commands:
>
> - `npx prisma db push` (DISALLOWED)
> - `npx prisma migrate dev` (DISALLOWED)
> - `npx prisma migrate reset` (DISALLOWED)

(Copied word for word from `CLAUDE.md`, which stays the source.)

### Schema changes

Schema changes ship as idempotent SQL in `prisma/manual/<ticket>.sql`, plus the matching `schema.prisma` edit ([[0002-manual-sql-schema-changes]]).

`prisma.config.ts` reads `.env.development.local`, then `.env.local`, then `.env` (the first file that sets a variable wins, and variables already in the shell win over all of them). Apply the file over the direct connection, because the pooler on :6543 hangs on `db execute`:

```bash
DATABASE_URL="$(grep -E '^DIRECT_URL=' .env.development.local | cut -d= -f2- | tr -d '"')" \
  node --env-file=.env.development.local node_modules/prisma/build/index.js db execute --file prisma/manual/<file>.sql
```

### Schema and config rules

- `prisma/schema.prisma` uses `snake_case` DB columns and tables (`@map` / `@@map`) with PascalCase Prisma model names, e.g. model `User` maps to table `users`. Exceptions: `campus` and the `bystander_*` models keep the table name as the model name.
- IDs are DB-generated UUIDs (`dbgenerated("gen_random_uuid()")`).
- The Prisma client is regenerated by `npx prisma generate`, which also runs automatically on `postinstall`. The generator sets no `output`, so the client goes to `node_modules` and code imports `@prisma/client`. Never hand-edit the generated client. (Older `CLAUDE.md` said `src/generated/`; that folder doesn't exist.)
- Prisma config lives in `prisma.config.ts` (not `package.json`), using `DATABASE_URL` and `SHADOW_DATABASE_URL`.

### Seeds

- `npm run seed` (`tsx prisma/seed.ts`) seeds the lookup data.
- `npm run seed:matatag` seeds the MATATAG checklist from `prisma/data/matatag-2025-07-25.ts`. It can be re-run safely: it matches by code and never deletes, so item ids stay stable ([[assessments]]).

### The clients

- `src/lib/prisma.ts`: the server-side Prisma client (through `@prisma/adapter-pg`), used from server actions for all reads and writes.
- `src/lib/supabase.ts`: the browser Supabase client, for auth only (see [[architecture]]).
- `src/lib/supabase-admin.ts`: the server-side service-role client, only for what Prisma can't do.

## Data

Models by domain (model, table in parentheses):

- People: `User` (`users`), `UserType` (`user_types`), `Position` (`positions`).
- Places: `campus` (`campus`), `Cluster` (`clusters`, unique `name`), `Unit` (`units`, unique `name` + `cluster_id`).
- Events: `Event` (`events`, `campus_id`, `status_id`, `user_id` creator, `completed_by`), `EventStatus` (`event_statuses`).
- Field reports: `Report` (`reports`: `event_id`, `cluster_id`, `unit_id`, legacy headcount int columns, `damage_condition_id`, `damage_photo_paths`, location), `ReportCasualty` (`report_casualties`, with `photo_paths`), `ReportMissingPerson` (`report_missing_persons`), `ReportPopulationCount` (`report_population_counts`, unique `report_id` + `category_id`).
- Bystander reports: `bystander_reports` (`contact_number`, `photo_paths`), `bystander_incident_types`, `bystander_report_statuses`, `BystanderReportPopulationCount` (`bystander_report_population_counts`). Casualties and missing persons reuse `ReportCasualty` / `ReportMissingPerson` through `bystander_report_id`.
- Lookups: `CasualtyCondition` (`casualty_conditions`), `DamageCondition` (`damage_conditions`), `PopulationCategory` (`population_categories`), `CampusPopulationCategory` (`campus_population_categories`).
- Assessments: enums `AssessmentAnswer` (yes/no/na), `AssessmentSafeAnswer`, `AssessmentVersionStatus` (draft/published/retired); `DrrmPillar` (`drrm_pillars`), `BuildingAreaType` (`building_area_types`), `AssessmentTemplate`, `AssessmentTemplateVersion`, `AssessmentSection`, `AssessmentItem`, `Building` (`buildings`), `BuildingArea`, `Assessment` (`assessments`, unique `client_ref`), `AssessmentArea`, `AssessmentAnswerRow` (`assessment_answers`), `AssessmentPillarScore`, `AssessmentSectionComment`.

All ids are `uuid` with `dbgenerated("gen_random_uuid()")`. Columns are `snake_case`; most models are PascalCase with `@@map`, but `campus` and the `bystander_*` models keep the table name as the model name.

## Server actions

None live here. Every module's `src/actions/<domain>/index.ts` imports `prisma` from `src/lib/prisma.ts`. `toFriendlyError` turns `P2003` (still in use), `P2002` (already exists) and `P2025` (not found) into readable messages; actions call it as `toFriendlyError(err, '<label>')`.

`supabaseAdmin` is used for `auth.admin.createUser` / `deleteUser` ([[users]]), `auth.getUser(token)` (`requireProfile`, [[auth]]) and the private `bystander-photos` and `report-photos` Storage buckets (`src/lib/photo-storage.ts`, [[bystander-reports]], [[field-reports]]).

## Client side

- The browser never imports `prisma`. It uses `supabase` from `src/lib/supabase.ts` for auth only, and `getAccessToken()` to pass the token to token-verified actions.
- Forms use `react-hook-form` with `zodResolver` and the schemas in `src/lib/schemas.ts` (sign-in and password, user, event, report and casualty, bystander report, cluster, unit, building, position, campus, conditions, population category, assessment payload and details, checklist draft, section, item and area type).
- TanStack Query defaults (`src/components/providers.tsx`): `staleTime` 60 s, `retry` 1.

## Rules and gotchas

- Change the schema with a new idempotent file in `prisma/manual/` plus the matching `schema.prisma` edit. Never `prisma db push`, `migrate dev` or `migrate reset`.
- Apply a manual file over the direct connection (`DIRECT_URL`, port 5432); `db execute` hangs on the pooler (6543). Production runs it in the Supabase SQL editor before the deploy.
- Some constraints exist only in SQL: `CHECK`s on `bystander_reports.contact_number` and `photo_paths` (max 3), `reports.damage_photo_paths` and `report_casualties.photo_paths` (max 3), population count `>= 0`, assessment item pillar rules, `floor_count >= 1`, `ended_at >= started_at`, and the one-published-version unique index. Prisma does not know them.
- The generated client goes to the default `@prisma/client` (no `output` in the generator) and code imports from `@prisma/client`; `postinstall` runs `prisma generate`.
- `prisma/seed.ts` connects with `SHADOW_DATABASE_URL`, not `DATABASE_URL`. It writes every cluster and event to the fixed campus id `f5b2b08d-d24a-4fbc-af3a-defe18b8f03d`. Lookups use `createMany` with `skipDuplicates`, but events are `create`d, so re-running adds duplicate NSED events.
- `supabase-admin.ts` holds the service-role key. Import it only from server code.
- `Report` still has the fixed headcount columns (`faculty_members` … `guests`, listed in `HEADCOUNT_FIELDS`) beside the per-campus `ReportPopulationCount` rows.
